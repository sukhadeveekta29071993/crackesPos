# RCA — Admin login failure on sparkle-cart-9 (https://sparkle-cart-9.emergent.host)

## Problem statement
User reports admin cannot log in on the live app. A prior session concluded the user was typing the wrong email (correct: admin@crackerpos.in / admin123). User still reports failure. Asked to check backend health, admin user existence, brute-force lock state, and 401/429 on POST /api/auth/login.

## Investigation & evidence (active run 066aee34-dbdd-4bae-97d8-4a40653f3836)

### 1) Backend running & healthy — YES
- App logs show live traffic being served, including `POST /api/auth/login HTTP/1.1 200 OK` multiple times, and the most recent login attempt (last 180 min) was `200 OK`.
- Note: `preview_health_check /api/health` returned 404, and internal probes to `/health` also 404. This is just a missing health route — the backend is up and serving. Not related to the login issue.

### 3) Brute-force lock state — admin@crackerpos.in is NOT locked
Important: the lock table `login_attempts` is keyed on the login **identifier (email)**, NOT on IP address. (Each doc = {identifier, count, locked_until}. 15-min window confirmed: updated_at 06:07:29 → locked_until 06:22:29.)

Current lock/attempt records:

A targeted query for the correct email returned **no record for `admin@crackerpos.in`** (the only "crackerpos" match is the typo `admin@firecrackerpos.in`). So the correct admin email has never accumulated failures and is **not locked**.

### 4) 401 / 429 on POST /api/auth/login
- **Zero 429 responses** anywhere in the logs (status histogram: 200×7, 401×35, 404×158 over the window). No brute-force 429 is being emitted against the admin flow.
- The 401s are overwhelmingly on `/api/admin/*`, `/api/auth/me`, and `/api/auth/refresh` — normal "no/expired token" responses, not login failures.
- A few historical `POST /api/auth/login 401`s exist, consistent with the typo'd emails above.

## Root cause
Same as the previous session: the user is logging in with the **wrong email**. The lock table literally captured the typo variants being entered — `admin@crackerpod.in` (should be cracker**pos**, not cracker**pod**) and `admin@firecrackerpos.in`. The correct account `admin@crackerpos.in` exists, is approved/admin, is **not locked**, and successfully logs in (200 OK observed on the login endpoint, including the most recent attempt).

Correction to the reported mental model: the brute-force protection is keyed by **email identifier**, not IP. There is no IP lock on the user to clear, and the "Locked IPs" panel will not list their IP. If the stray typo entries need clearing they are per-email, but they do not block the correct email.
